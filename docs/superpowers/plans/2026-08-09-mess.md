# Mess Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

## Status: COMPLETE

`pet_mess_check` is registered in `simulator/CMakeLists.txt` and passing.
Everything this plan's own "what this deliberately does NOT do" section
named as future work is also done now — see that section's notes, including
the later split of `kf_pet_clean()` into `kf_pet_bath()`/`kf_pet_flush()`.

**Goal:** Add the fourth care type — mess — as two mechanics: discrete poops that appear on a timer and sit until cleared, and a dirtiness value that rises over time and faster while poops are lying around.

**Architecture:** Mess lives in `kf_pet_state` beside the three needs, and advances inside `apply_stage_segment()` alongside them, so offline fast-forward covers it for free. Poops are a count, not a list — position is presentation, not simulation. A new `kf_pet_clean()` care action joins feed/play/rest.

**Tech Stack:** C++17, no exceptions, no RTTI. Core is heap-free.

## Global Constraints

- **HakoniwaOS is always one token.**
- **Core stays heap-free.** `python3 tools/check_no_heap.py .` must keep reporting `core is heap-free`.
- **Zero warnings** on both desktop (`-DKAMIFRAME_WARNINGS_AS_ERRORS=ON`) and device (ESP-IDF `-Wall -Wextra -Werror`).
- **All existing ctest cases must pass.** There are **17** as of the evolution-tree work landing; confirm the count yourself before starting.
- **The save format version must rise** — `kf_pet_state` gains fields. An older save must be refused, not misread.
- Millipercent scale: 100000 mp = 100%, as the needs already use.

## The design being implemented

From `docs/superpowers/specs/2026-08-09-core-care-loop-design.md` section 4:

> **Poops** are discrete objects. They appear on a timer (sooner after eating), sit on screen until cleared, and accumulate. The mess *is* the state — visible across the room, no bar to read.
>
> **Dirtiness** is a continuous value that rises over time and faster while poops are lying around. At thresholds it becomes visible: flies first, then stink lines.

**Out of scope for this plan:** sickness and death (which mess feeds into — that is the next plan), care variations, and any screen change. The simulation gains mess; drawing it comes later.

- [ ] **Step 1: Write the failing test**

Add to `simulator/src/headless/headless_main.cpp`, before `run_pet_screen_check`, following the surrounding style (including the trailing `std::printf("%s\n", ok ? "PASS" : "FAIL");` every other check has):

```cpp
/* Poops are a COUNT, not a list. Where each one sits on screen is
 * presentation and belongs to the screen; the simulation only needs to know
 * how many are waiting. That is what makes this survive offline
 * fast-forward without storing anything per-poop. */
int run_pet_mess_check(void) {
    bool ok = true;
    auto check = [&ok](bool cond, const char *what) {
        if (!cond) {
            KF_LOGE(TAG, "FAILED: %s", what);
            ok = false;
        }
    };

    kf_pet_config config = kf_pet_default_config();

    kf_pet_state pet{};
    kf_pet_init(&pet);
    pet.stage = KF_PET_STAGE_CHILD;   /* eggs and babies still decay-exempt */
    check(pet.poop_count == 0u, "a fresh pet has not pooped");

    /* Long enough for several intervals, in one segment. */
    apply_stage_segment_for_test(&pet, &config, config.poop_interval_seconds * 3u);
    check(pet.poop_count >= 3u, "poops accumulate over time");

    /* They pile up, but not without limit -- an unbounded count would
     * eventually overflow the screen and mean nothing extra. */
    apply_stage_segment_for_test(&pet, &config, config.poop_interval_seconds * 100u);
    check(pet.poop_count == KF_PET_MAX_POOPS, "poop count saturates rather than growing forever");

    /* Cleaning clears all of them. */
    kf_pet_clean(&pet);
    check(pet.poop_count == 0u, "cleaning clears every poop");

    /* Feeding brings the next one sooner. */
    kf_pet_state fed{};
    kf_pet_init(&fed);
    fed.stage = KF_PET_STAGE_CHILD;
    kf_pet_feed(&fed);
    check(fed.seconds_until_next_poop == config.poop_interval_after_feed_seconds,
          "feeding shortens the wait for the next poop");
    check(config.poop_interval_after_feed_seconds < config.poop_interval_seconds,
          "the after-feed interval really is shorter");

    std::printf("%s\n", ok ? "PASS" : "FAIL");
    return ok ? 0 : 1;
}
```

a `--verify-mess` argument branch, a usage line, a dispatch, and
`add_test(NAME pet_mess_check COMMAND kamiframe-headless --verify-mess)` in
`simulator/CMakeLists.txt`.

- [ ] **Step 3: Add the state and the constant**

In `hakoniwaos/include/kf/pet.h`, near `KF_PET_STAGE_COUNT`:

```c
/* How many poops can be waiting at once.
 *
 * Bounded on purpose. An unbounded count would overflow any screen that
 * tries to draw them, and past a handful it stops communicating anything a
 * player did not already know -- "you have not cleaned up" is the whole
 * message, and eight says it as clearly as eighty. */
#define KF_PET_MAX_POOPS 8u
```

In `kf_pet_state`, beside the needs:

```c
    /* How many poops are waiting to be cleaned, 0..KF_PET_MAX_POOPS.
     *
     * A COUNT, not a list. Where each one sits on screen is presentation and
     * belongs to the screen, which can place them from this number however
     * it likes. Keeping it a count is also what lets offline fast-forward
     * work without storing anything per-poop across a save. */
    uint8_t poop_count;

    /* Seconds remaining until the next poop appears. Counts down inside
     * apply_stage_segment(), so a device that was switched off for a day
     * comes back to a correctly messy pet rather than a clean one. */
    uint32_t seconds_until_next_poop;
```

In `kf_pet_config`, beside the stage rates:

```c
    /* How long between poops normally, and how long after a meal. Feeding
     * shortens the wait, which is what ties the mess mechanic to the care
     * loop rather than leaving it on an unrelated timer. */
    uint32_t poop_interval_seconds;
    uint32_t poop_interval_after_feed_seconds;
```

- [ ] **Step 5: Advance the timer**

In `apply_stage_segment()`, after the existing need decay and before the
personality accumulation, add:

```cpp
    /* Mess advances with the needs, inside the same segment loop, so offline
     * fast-forward covers it without a second code path. A pet left in a
     * drawer for a day comes back correctly filthy. */
    if (state->seconds_until_next_poop == 0u) {
        state->seconds_until_next_poop = config->poop_interval_seconds;
    }
    uint32_t remaining = segment;
    while (remaining >= state->seconds_until_next_poop) {
        remaining -= state->seconds_until_next_poop;
        state->seconds_until_next_poop = config->poop_interval_seconds;
        if (state->poop_count < KF_PET_MAX_POOPS) {
            state->poop_count++;
        }
    }
    state->seconds_until_next_poop -= remaining;
```

Note the loop terminates because `poop_interval_seconds` is non-zero by
construction; if a misconfigured zero ever reached here it would spin. Guard
it: immediately before the loop, add

```cpp
    if (config->poop_interval_seconds == 0u) {
        return; /* misconfigured: no mess rather than an infinite loop */
    }
```

- [ ] **Step 6: Shorten the timer on feeding, and add the clean action**

In `kf_pet_feed()`, after the existing restore and the
`care_actions_taken` increment:

```cpp
    /* Eating brings the next mess forward. Only ever shortens the wait --
     * feeding repeatedly should not be able to push mess further away. */
    const kf_pet_config config = kf_pet_default_config();
    if (state->seconds_until_next_poop > config.poop_interval_after_feed_seconds) {
        state->seconds_until_next_poop = config.poop_interval_after_feed_seconds;
    }
```

Add the new action beside `kf_pet_rest()`:

```cpp
void kf_pet_clean(kf_pet_state *state) {
    if (state->care_actions_taken < UINT32_MAX) {
        state->care_actions_taken++;
    }
    state->poop_count = 0u;
}
```

and declare it in `kf/pet.h` beside the other three:

```c
/* Clears every waiting poop. Counts as care, like the other three -- a
 * creature you clean up after is one you have interacted with, which is what
 * separates it from the never-touched path to the dust form. */
void kf_pet_clean(kf_pet_state *state);
```

- [ ] **Step 1: Write the failing test**

```cpp
/* Dirtiness is the continuous half of mess, and it is deliberately NOT a
 * fourth need bar -- it has no restore action of its own, it rises faster
 * the more poops are waiting, and it shows itself as flies and stink lines
 * rather than a number. See the care-loop spec's section 4. */
int run_pet_dirtiness_check(void) {
    bool ok = true;
    auto check = [&ok](bool cond, const char *what) {
        if (!cond) {
            KF_LOGE(TAG, "FAILED: %s", what);
            ok = false;
        }
    };

    kf_pet_config config = kf_pet_default_config();

    kf_pet_state clean_pet{};
    kf_pet_init(&clean_pet);
    clean_pet.stage = KF_PET_STAGE_CHILD;

    kf_pet_state messy{};
    kf_pet_init(&messy);
    messy.stage = KF_PET_STAGE_CHILD;

    /* Same elapsed time; the messy one starts with poops already down.
     * Poops are cleared each iteration on the clean pet so the ONLY
     * difference between them is the mess. */
    constexpr uint32_t kHour = 3600u;
    apply_stage_segment_for_test(&clean_pet, &config, kHour);
    clean_pet.poop_count = 0u;

    messy.poop_count = KF_PET_MAX_POOPS;
    apply_stage_segment_for_test(&messy, &config, kHour);

    check(clean_pet.dirtiness_mp > 0u, "a pet gets dirty just by existing");
    check(messy.dirtiness_mp > clean_pet.dirtiness_mp,
          "poops on the floor make it dirty faster");

    check(KF_PET_DIRTY_FLIES_MP < KF_PET_DIRTY_STINK_MP,
          "flies show up before stink lines");

    /* Cleaning resets it. */
    kf_pet_clean(&messy);
    check(messy.dirtiness_mp == 0u, "cleaning also washes the creature");

    std::printf("%s\n", ok ? "PASS" : "FAIL");
    return ok ? 0 : 1;
}
```

Wire it in as `--verify-dirtiness` / `pet_dirtiness_check`, same as before.

     * rather than wrapping. */
    const uint64_t rise_per_hour =
        static_cast<uint64_t>(config->dirtiness_rise_mp_per_hour) +
        (static_cast<uint64_t>(config->dirtiness_rise_per_poop_mp_per_hour) *
         state->poop_count);
    const uint64_t rise = (rise_per_hour * segment) / 3600u;
    if (rise >= KF_PET_MILLIPERCENT_MAX - state->dirtiness_mp) {
        state->dirtiness_mp = KF_PET_MILLIPERCENT_MAX;

        state->dirtiness_mp = static_cast<kf_pet_millipercent>(
            state->dirtiness_mp + rise);
    }

## What this plan deliberately does NOT do

- **Sickness and death.** Mess feeds them; that was the next plan, and is
  done — see `2026-08-09-sickness-and-death.md`.
- **Care variations — at the time this plan was written.** The clean action
  added here took no variation argument yet. Since done: the care-variations
  plan split `kf_pet_clean()` into `kf_pet_bath()` (which takes a variation)
  and `kf_pet_flush()` (which, by design, still does not — see
  `kf/pet.h`'s comment on why flush has no opinion).
- **Any screen change — at the time this plan was written.** Nothing drew
  poops, flies or stink lines then. **Built since:** poops are drawn as
  discrete scene objects (`simulator/src/pet/kf_creature_screen.cpp`).
- **The Lua API — at the time this plan was written.** `kf_pet_clean()` was
  not exposed to scripts. It no longer exists; its replacements are: both
  `pet.bath()` and `pet.flush()` are bound (`sdk/lua/kf_lua_port.cpp`).
